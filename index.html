Exhibit 002 · The questions ordinary search misses

Search finds files. You want to know what happened.

Nobody wakes up wanting semantic search. People want to know where the proof is, which version stands, what the record says on a date, and what it does not say. Those are memory questions: several artifacts, a chronology, a source that outranks another, and a way to inspect the proof. That is what docenta is built for.

Local evidence, exact receipts, explicit conflicts and gaps, served to the agent you already use. Built for evidence questions ordinary search misses. A docent is the museum guide you ask about a collection. Your corpus gets one.

The one question that sums it up, and the one a retrieval box bolted onto a chatbot cannot answer: what do my own records actually prove about this, and what do they not prove? It needs the sources ranked, dated and compared, the contradiction kept visible, and an honest "not established" at the end. That is the whole product.

Exhibit 003 · Receipts, every time

Answers come with receipts. Five kinds.

Answer receiptThe exact source, the exact span, page or message behind every claim.
Timeline receiptEvery event on the timeline carries the source that dates it.
Version receiptOld and new side by side: what changed, and which one stands.
Conflict receiptBoth contradicting sources visible. Never smoothed into one confident sentence.
Gap receiptWhat was searched and what the collection does not establish. "I don't know" you can trust.

Gaps disclosed, never papered over. When the corpus cannot answer, docenta says so, shows what it did find, and names the document that would settle it.

Exhibit 004 · Ask the sensitive question

Ask the sensitive question without first uploading the sensitive file.

The matter file, the claim, the mail archive, the private source tree, the unpublished paper, the household folder: docenta ingests, indexes and answers on your own hardware. Originals are never copied; only searchable derivatives are stored. Your agent gets a small evidence pack with the receipts, not your archive. It gets it over MCP, the connector standard it already speaks, from a server that runs on your own machine: your agent talks to a local process, not to a URL in someone's cloud. The only remote MCP addresses on this site are the public doors, sealed collections we host on purpose; your own collection never has one. Zero uploads, zero telemetry, and the token budget is printed on every answer.

Exhibit 007 · How the docent works

A spine that ingests, three channels that answer, one artifact that proves it.

ingest walk → hash → extract → index · containers explode into members · re-scan costs O(changes)
channels exact BM25 · paragraph lexical · dense vectors, fused and re-ranked · entities, timelines, themes on top
answer evidence_pack: route plan, cited spans, conflicts, disclosed gaps, enforced token budget
live mail, chat exports, git and agent sessions stream in every hour · your corpus feeds itself
tools search search_meaning evidence read thread related who_is timeline verify_quote status and ten more, over MCP · every page says what was searched, what was dropped and why, and how many documents held every term

The same 48 judged questions over the same corpus, asked by the same scripted agent two ways. With the evidence pack it cited the right document on 44 of 48, in 1 to 2.5 tool calls per task. Limited to search-and-fetch loops, the way an agent works without the pack, it cited it on 39 of 48, in more calls. The difference is what the agent is handed: not a hit to go and read, but the evidence itself, the cited spans, the dates, the conflict and the gap, assembled and ranked, so the first answer is the deep one. What each pack used is printed on it. The lexical, entity and timeline layers are deterministic: a re-run gives the same bytes.

Exhibit 008 · What docenta reads today · 0.3.1

Everything on the machine, by what it is.

One engine, every lane. Originals stay where they are; docenta keeps searchable derivatives and a map back to the path. The list below is what the current build reads, as the handbook states it.

Files.

Text, Markdown, PDF, Office, ODF, RTF, property lists, XML, JSON record by record, archives down to their members. The author, the dates and the sensitivity label of a document; the time and place inside a photo; ten copies of one file cost one index entry.

Mail.

A Takeout or mbox export in an evening, then the live account every hour: Sign in with Google for Gmail and Workspace, an app password elsewhere, Apple Mail and Outlook messages read as mail. Every folder the server lists, attachments as members, labels kept.

Chats and agent sessions.

Claude Code, Codex, ChatGPT and claude.ai exports, WhatsApp drops: every session rendered as it happens, so what the last agent learned is one search away for the next, and a compaction loses nothing.

Git.

Every repository on the machine, end to end: each commit rendered as correspondence with the files it changed, so a hash finds its commit and a line finds the message that introduced it.

Scans and photos.

OCR over scanned PDFs, images, HEIC and camera RAW previews, the pictures inside documents and animated images, on the machine's own GPU where it has one; a warning where a page's text order is unreliable.

Code.

C, C++, Go, Java, JavaScript, Kotlin, Python, Rust and TypeScript parsed by structure: functions, forms and identifiers as terms, with the commit and the thread that explain a line.

Runs on macOS (Apple silicon and Intel), Windows and Linux, identically. Speaks MCP to Claude Code, Claude, ChatGPT, Codex, Cursor and VS Code. People, places and dates become entities with timelines; meaning search works across languages; a rented GPU takes the heavy arithmetic for an hour on your say-so, sealed. The handbook is the full account.
